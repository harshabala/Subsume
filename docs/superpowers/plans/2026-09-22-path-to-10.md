## Task 1: Encrypt API keys at rest

**Why:** Roast flagged plaintext API keys explicitly under Technical Execution (8/10, capped by this). `grep` on `src/background/storage.ts` confirms keys still go into `chrome.storage` with no wrapping.

**Files:** `src/background/storage.ts`, wherever `apiKey`/provider keys are read/written (`src/ui/pages/Settings.tsx`, provider clients), new `src/shared/keyCrypto.ts`.

**Requirements:**
1. Wrap stored API key values with the WebCrypto `SubtleCrypto` API (AES-GCM) using a per-install key derived and stored in `chrome.storage.local` separately from the ciphertext (this defends against casual disk/sync inspection and other extensions reading storage directly, not against a compromised profile — document that limit in a code comment, not marketing copy).
2. Migrate existing plaintext keys on first read after upgrade: detect unencrypted value, encrypt in place, write back once.
3. Never log key material, even encrypted, through `src/shared/logger.ts` / `diagnosticLog.ts`.
4. Settings UI must not regress: masked display, paste, clear, and "test connection" flows all still work.

**Tests:** round-trip encrypt/decrypt unit test; migration test (plaintext in storage → read → now encrypted); logger redaction test asserting key material never appears in diagnostic log output.

**Acceptance:** no plaintext API key ever written to `chrome.storage` after this ships; existing users' keys migrate silently with no re-entry required.

## Task 6: Make export honest but re-import costly

**Why:** Roast: "Local library is real switching cost only after months... export is good ethics; re-import elsewhere must hurt." This is the one moat lever code can actually pull.

**Requirements:**
1. Audit current export format (`src/background/handlers/library.ts` or wherever export lives). Keep it complete and user-owned — never make export lossy or gated. That stays an ethical line, not a growth lever.
2. Identify what's *structurally* Subsume-specific and expensive to rebuild elsewhere: cross-medium linking between a film and a book, weekly-selection history, reflection timestamps tied to detection events, local activation streaks. Confirm these are included in export (so the user owns them) but note in a short doc (`docs/EXPORT_MOAT.md`) which of these a competitor's importer would have to reverse-engineer to replicate — i.e., the moat is "we linked your data richly," not "we withhold your data."
3. No code change required if the audit shows this is already true — write the doc either way so this is a documented, deliberate position instead of an accident.

**Acceptance:** `docs/EXPORT_MOAT.md` exists, export remains 100% complete and user-owned, and the moat argument is written down instead of implied.
